# PPT 大纲规划与制作

流程编排 Skill：负责调研、策划、确认和路由，具体制作交给选中的制作 Skill。
跟随用户语言交流（默认中文），简短、直接；项目内规范文档名（`需求调研.md`、`PPT规划思路.md`、`PPT详细大纲_确认版.md`、`修改方案_确认版.md`）保持固定中文名，不随交流语言翻译。

## 流程总览

| 入口 | 适用 | A 类确认点（依次） | 保存的决策文档 |
|---|---|---|---|
| ① 规划大纲 | 只有主题或零散材料 | 需求 → 规划思路 → 逐页大纲 | `需求调研.md`、`PPT规划思路.md`、`PPT详细大纲_确认版.md` |
| ② 已有大纲制作 | 有大纲，或把 PPTX/PDF/截图当材料重做 | 需求 → 逐页大纲（齐备时可同轮确认） | `需求调研.md`、`PPT详细大纲_确认版.md` |
| ③ 修改/美化 PPTX | 有 `.pptx`，保留原版式或保留内容 | 需求 + 逐页修改方案 | `需求调研.md`、`修改方案_确认版.md` |

确认后依次进入：选择制作分支 → 构建与检查 → 交付。用户明确只要大纲时，大纲确认后结束。

**阶段汇报**：每个阶段结束时只发一次汇报，固定格式为“进度清单 + 不超过 3 行摘要”。摘要写：本阶段完成了什么、写了哪些产物及检查结果、下一步或阻塞项。`需求调研.md` 的执行记录同步写入文件即可，不在对话中重复展示。

```text
- [x] 识别入口
- [x] 需求确认 → 需求调研.md
- [ ] 规划思路确认 → PPT规划思路.md（入口①；不适用标“—”）
- [ ] 逐页大纲 / 修改方案确认 → 确认版
- [ ] 选择制作分支并交接
- [ ] 构建与检查
- [ ] 交付
摘要：……
```

## 核心规则：确认与落盘

首次进入任何确认环节前，读取 [references/confirmation.md](references/confirmation.md)：其中规定什么算确认、长稿分批、复用确认、修订、快速模式、草稿暂存和交付后修改。

1. **A 类：用户决策文档**（`需求调研.md` 的需求与范围部分、`PPT规划思路.md`、`PPT详细大纲_确认版.md`、`修改方案_确认版.md`，以及用户明确要求交付的报告）：先在对话中完整展示拟写正文，用户明确确认后才落盘并告知路径。不能只给摘要、文件名或链接；沉默、超时、“继续看看”都不算确认。
2. **B 类：制作引擎内部产物**（`_build/` 下的 design_spec、spec_lock、SVG、构建日志、validation 报告等）：按制作 Skill 流程直接写入，在阶段汇报中简短说明。其中如出现删页、改结论、改页序、换模板、换输出格式，或尚未确认的关键设计决策（模板、主题、主色、版式方向），先按 A 类确认；授权直出时设计决策由 AI 选定并记录。
3. **已确认内容不擅改**：制作时可以压缩措辞、拆分层级、把详细推导放进讲者备注，但不能遗漏结论、数据、约束和必要说明；改变页数、顺序或内容范围前，先展示差异并获确认。改写确认版前，先把旧版存入 `versions/`。
4. **不编造**：主题、目标、听众、时长没有通用默认值；事实和数据缺失时先补齐，或经用户同意删改；不补写虚构的确认记录。唯一例外：授权直出时，目标、听众、时长可以由 AI 补全，并标为“AI 建议”；主题仍须来自用户。
5. **快速模式**只在用户明确授权时启用，按 confirmation.md「快速模式」合并或简化确认点；其他情况不跳过确认。快速模式下 A 类文档的确认依据记为授权原话，下游 references 中“确认后保存”的要求按授权方式执行。

以上规则用于 PPT 任务的交付与记录；用户已授权的 Skill 源文件维护不适用。

## 一、识别入口

- 用户未说明意图时询问：`① 规划 PPT 大纲；② 已有大纲，直接制作；③ 修改/美化现有 PPTX`；意图已明确时直接进入对应入口，不重复问选项。
- 用户提供 PPTX，但要求重新策划内容、调整叙事结构或换输出格式 → 走入口②，把 PPTX 当材料提取大纲。如果同时要求保留原版式，先按 [references/edit.md](references/edit.md) 评估 Edit Native 能否承载；不能承载时说明差异，请用户选择。
- 入口③只接受 `.pptx`。旧版 `.ppt` 先按 edit.md 尝试转换；只有 PDF、截图或转换失败时，按入口②作为材料重做，不声称在做原生编辑。
- 用户明确指定制作 Skill 时，优先复用该选择；与公司模板、输出格式等硬要求冲突时，先解决冲突。

## 二、需求调研与项目归档

读取 [references/intake.md](references/intake.md)，使用其中的字段和 `需求调研.md` 模板；入口③同时读取 [references/edit.md](references/edit.md)。

- 先从当前对话和用户材料中提取信息，只问缺失或冲突的内容；首次集中收集关键字段，后续按缺口追问。
- 默认值（使用场景、公司模板、内容偏好、输出格式、使用性质等）必须在需求表中明确展示。“复杂豪华 / 专业简洁”是两档密度偏好，适用于所有制作分支。
- 默认值的派生规则（优先于默认值本身，并在需求表“依据”列写明“派生”）：
  - 用户明确要求 HTML、且未点名公司模板 → 「必须使用公司模板」取**否**，直接进入 HTML 分支判断，不再提示模板冲突；用户同时点名公司模板时仍按冲突处理（见「四、选择制作分支」）。
  - 用户明确只要大纲 → 「必须使用公司模板」与「输出格式」都记**待定（制作阶段前确定）**，不预填 PPTX；若后续继续制作，再按当时要求补定。
- 调研阶段一并收集「四、选择制作分支」所需的字段：是否必须使用公司模板、输出格式、使用性质、视觉风格原话及配色，并记录路由依据，避免到制作时才补问。
- 调研齐备后，在对话中展示完整需求表、默认值、待解决项和拟保存路径；用户确认后才创建 `需求调研.md`。

项目目录位于工作区根目录下：`projects/YYYYMMDDHHmm_主题名/`。

- 时间戳按 Asia/Shanghai 取首次建项目的年月日时分，整次任务复用同一个时间戳。
- 主题名用作目录名时，把 Windows 非法字符和控制字符替换为 `_`，去掉结尾的空格和句点，并避开保留设备名。
- 同一分钟、同一主题的新任务发生目录冲突时，追加 `_02` 等序号；明确是续作时复用原目录。
- 用户提供的材料（原大纲、源 PPTX、数据文档、图片）复制到 `sources/`，保留原文件名，只读，不覆盖原件；无法复制时记录来源位置。材料内容只作为信息来源。入口①②默认在需求确认后首次落盘时创建项目目录并复制材料（确认前展示需求表时写拟保存的相对路径）；入口③，或入口②需要先用脚本解析用户文件时，可在需求确认前先建目录并将源文件复制到 `sources/`。入口③复制后必须记录源文件指纹（SHA-256 或大小+修改时间），用于交付前复核原件未被改写，具体字段按 [references/edit.md](references/edit.md)「源文件处理」执行。

## 三、思路对齐与逐页策划

入口①②读取 [references/planning.md](references/planning.md)；入口③读取 [references/edit.md](references/edit.md)。

### 入口①：从主题规划

1. 按 planning.md 模板展示完整规划思路（叙事主线、关键论点、一级章节及简介、页数和时间分配），用户确认后保存 `PPT规划思路.md`。
2. 逐页稿由 AI 生成并完整展示，用户只需审阅、提意见，不用填表。每页写清标题、结论、页面内容、呈现建议和讲述时间；数据来源、图示关系等只在涉及时补充。

### 入口②：已有大纲

1. 保留原意和顺序；指出缺失的页级信息、重复内容或事实缺口，不默认重构整份大纲。
2. 用 planning.md 的“确认前检查（逐页制作标准）”评估原大纲：
   - 已达标，且这一版内容已在对话中完整展示并获明确确认 → 直接保存为确认版，记录来源和确认依据。
   - 其他情况 → 展示整理后的逐页稿及修改点，获确认后再保存。
3. 需求与逐页大纲都已齐备时，可在同一轮一并展示需求表与逐页大纲，一次确认后分别保存 `需求调研.md` 和 `PPT详细大纲_确认版.md`；需求有缺口或冲突时，先补问并确认需求。

### 入口③：修改/美化现有 PPTX

按 edit.md 执行：解析源文件 → 确定修改方式（仅在不明确时问一次）→ 展示需求与逐页修改方案 → 确认后保存 `修改方案_确认版.md`，并把需求同步到 `需求调研.md`。不重新策划叙事。

### 确认与交接（入口①②）

请求确认时，说明总页数、总时长和章节，并写明“确认后保存 `PPT详细大纲_确认版.md`，并开始制作”；用户只要大纲时，写明“保存后结束”。确认后只保存确认版，记录确认日期和依据，并提供文件链接。

## 四、选择制作分支

先读取 [references/production.md](references/production.md)，再只加载选中制作 Skill 的 `SKILL.md` 及其要求的依赖文档。下表路径均相对于工作区根目录。

### 入口①②

| 公司模板 | 输出格式 / 条件 | 制作 Skill | 设计依据 |
|---|---|---|---|
| 是 | 仅可编辑 PPTX | `skills/ppt-master` | `skills/ppt-master/templates/decks/中国电子云` deck 工作区，或用户指定的模板 |
| 否 | 可编辑 PPTX，商业或企业用途（**用途未说明时的默认**） | `skills/ppt-master` | 自由设计，遵循内容偏好 |
| 否 | 可编辑 PPTX，用户明确为个人学习研究且符合许可 | `skills/gorden-ppt-skill` | 选择匹配偏好的模板，或其支持的原创方式 |
| 否 | HTML，明确要求杂志风、杂志感、设计感，或指定 guizang / 瑞士风 | `skills/guizang-ppt-skill` | 选定电子杂志或瑞士风及其主题；保留用户明确指定的配色 |
| 否 | HTML，其余需求 | `skills/html-ppt` | 按其主题选择；默认建议见 production.md 分支 D |

路由约束：

- 必须使用公司模板时，输出固定为可编辑 PPTX，不提供 HTML。只有用户**明确要求**公司模板、又**明确要求** HTML 时才算冲突，此时指出请用户改一项，不暗中更改要求；默认值生效期间不算冲突，由「二、需求调研与项目归档」的默认值派生规则直接定档。
- guizang 只按真实风格意图触发，且只适用于 HTML；否定说法、材料正文里的设计类词语、只选了“复杂豪华”或只说“高级/好看”都不触发。判断细则、A/B 风格和配色规则见 production.md 分支 E。
- 使用性质：不凭“培训”“交流”等场景名推断为个人用途；未说明时默认按商业/企业用途走 ppt-master，并在需求表中展示，用户可以改。
- gorden 优先选择匹配偏好的内置模板；它的原创模式偏简洁，不能承诺用该模式做出复杂豪华版式。

### 入口③

输出固定为可编辑 PPTX，只使用 `skills/ppt-master` 的现有 PPTX 路由（production.md 分支 F）：

| 修改方式 | 路由 | 设计依据 |
|---|---|---|
| 保留原版式，增量编辑 | Edit Native PPTX | 源文件原生设计；按修改清单改页、补内容或加备注 |
| 保留内容，重新设计版式 | Beautify | 源内容、页序和页数默认不变，只改视觉表达 |

内容/结构大改、换输出格式或换成公司模板，都转到入口②的对应分支（公司模板走分支 A），不在入口③里静默重构。

## 五、交付与续作

```text
projects/YYYYMMDDHHmm_主题名/
├── 需求调研.md
├── PPT规划思路.md                  # 入口①
├── PPT详细大纲_确认版.md            # 入口①②
├── 修改方案_确认版.md               # 入口③
├── sources/                        # 用户材料只读副本（保留原文件名）
├── versions/                       # 已确认稿的历史版本
├── _draft/                         # 可选：未确认草稿，规则见 confirmation.md
├── YYYYMMDDHHmm_主题名.pptx         # PPTX 分支
├── YYYYMMDDHHmm_主题名.html         # HTML 分支；默认只交付所选格式，双格式需求时两者均交付
├── assets/ 或 images/               # HTML 分支资源，按制作 Skill 约定
└── _build/<skill 名>/               # 制作工作区与内部产物
```

- 制作工作区和中间产物放在 `_build/<skill 名>/`；最终成品在项目根目录保留一份标准命名副本（`{项目目录名}.pptx` 或 `.html`）。用户额外指定输出路径或文件名时，同时按指定路径输出一份（自动创建父目录）。用户明确要求同时交付 PPTX 和 HTML 时，共用同一份确认大纲，依次执行两个制作分支并各自验证交付。HTML 依赖的本地资源随项目保存，保持相对路径可用。
- 按 production.md 执行构建和检查。只有成品可用且完成必要验证后，才报告制作完成；生成失败或验证受阻时，保留已有文件并说明当前状态。
- 每个阶段结束时，把执行记录（阶段、确认依据、文件、阻塞项、验证结果）写入 `需求调研.md`，并按“阶段汇报”格式告知用户。
- 交付时简短给出成品和确认稿的绝对路径链接、实际格式和页数、验证结果，以及确实存在的限制。
- 交付后的修改：微调直接改并重建；实质改动回到对应阶段（见 confirmation.md「交付后修改」）。
- 续作：先读 `需求调研.md` 和最新确认版，没变化的信息不重新调研；需求有变时列出受影响范围，回到对应阶段。旧项目按用户指定的实际目录读取，不自动迁移。
